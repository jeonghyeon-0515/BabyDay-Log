# 전체 제품 플랜

작성일: 2026-04-03  
상태: Draft v1
기술 스택 전제: **Flutter + Supabase**

## 1. 제품 목표
BabyDay-Log의 1차 목표는 BabyTime의 핵심 경험을 재현하는 것이다.

### 목표 정의
- 부모가 하루 육아 운영을 기록/분석/공유/회고할 수 있다.
- 공동양육자가 같은 아이 데이터를 실시간으로 공유할 수 있다.
- 단순 로그가 아니라 패턴과 성장 변화를 읽을 수 있다.

## 2. 제품 원칙
1. **기록 속도 우선** — 입력은 최소 터치여야 한다.
2. **오늘 상태 우선** — 사용자는 복잡한 차트보다 먼저 “지금 아이 상태”를 알고 싶다.
3. **공동양육 우선** — 같은 아이를 여러 양육자가 함께 쓴다는 전제로 설계한다.
4. **비공개 기본값** — 커뮤니티 공개는 명시적 opt-in으로만 허용한다.
5. **원시 이벤트 보존** — 분석은 파생 결과이며, 원시 기록이 진실의 원천이다.

## 5. 왜 Supabase를 기준 스택으로 선택하는가
이 판단은 **Supabase 공식 기능 범위와 BabyTime 요구사항을 대조한 설계 판단**이다.

### Supabase가 잘 맞는 이유
- Flutter 공식 퀵스타트와 클라이언트 SDK를 제공한다.
- Auth / Database / Storage / Realtime / Edge Functions를 한 플랫폼에서 제공한다.
- RLS 기반으로 **아기/양육자/일기 공개 범위** 같은 세밀한 권한 모델을 설계하기 좋다.
- Storage도 RLS 정책으로 제어 가능해 아기 사진, 다이어리 첨부파일 보안에 적합하다.
- Realtime Broadcast는 공식 문서상 더 나은 확장성/보안을 위해 권장된다.

### 목표
- 기능 동등성 범위 확정
- 핵심 도메인 구조 확정
- 권한/공개 범위 규칙 확정

### 산출물
- 기능 벤치마크 문서
- IA
- 사용자 플로우
- ERD 초안
- 이벤트 타입 정의서
- 권한 정책 표
- 분석 지표 정의서

### 완료 기준
- 구현 전에 “무엇을, 어떤 순서로, 어떤 구조로 만들지”가 문서로 고정됨

## Phase 1 — 프로젝트 부트스트랩
기간: 1주

### 목표
- Flutter 앱과 Supabase 프로젝트의 기본 뼈대 확보

### 작업
- Flutter 앱 생성 및 기본 아키텍처 설정
- 환경 분리(dev/stage/prod)
- Supabase 프로젝트/로컬 개발 환경 설정
- Auth/Storage/Database/Realtime 기본 연결
- 디자인 토큰/다크모드 기본 테마
- 공통 라우팅/상태관리/에러 처리 구조

### 완료 기준
- 로그인 가능한 빈 앱 + Supabase 연결 + 기본 네비게이션 확보

## Phase 2 — 핵심 로그 기능
기간: 2~4주

### 목표
- BabyTime의 핵심인 기록 기능 usable 수준 완성

### 범위
- 사용자 로그인
- 아기 등록/전환
- 타임라인
- 활동 입력/수정/삭제
- 타이머 기반 기록
- Quick Memo
- 사진 첨부(최소 1차)

### 완료 기준
- 부모 1명이 아이 1~2명의 주요 활동을 안정적으로 기록 가능

## Phase 3 — 분석/성장
기간: 2~3주

### 범위
- 통계 대시보드
- 인터벌 분석
- 패턴 화면
- 성장 기록
- 성장곡선
- 백분위
- 월령별 발달 체크

### 완료 기준
- 기록된 이벤트가 신뢰 가능한 분석 결과로 연결됨

## Phase 4 — 공동양육/실시간
기간: 2~3주

### 범위
- 공동양육자 초대
- 초대 수락
- 역할 기반 접근
- 실시간 반영
- 충돌 처리 정책
- 알림/재동기화 기본형

### 완료 기준

## 9. 리스크와 대응

### 리스크 1. 로그 기능은 빨리 되지만 통계가 틀릴 수 있음
대응:
- 원시 이벤트와 집계 테이블을 분리한다.

### 리스크 2. 공동양육 권한이 꼬일 수 있음
대응:
- Household/Baby/CaregiverMembership 모델을 조기에 확정한다.

### 리스크 3. 사진/일기 공개 기능이 개인정보 리스크를 만든다
대응:
- 공개 기능은 비공개 로그와 별도 정책/버킷/모더레이션으로 분리한다.

### 리스크 4. 모든 기능을 한 번에 만들다가 출시가 지연될 수 있음
대응:
- P0/P1/P2를 유지하고, 각 Phase 완료 기준을 명확히 둔다.
